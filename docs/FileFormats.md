# SMRT File Formats

This document describes the mesh and characteristic-line files generated by the current SMRT release.

## Gmsh `.msh` files

SMRT uses Gmsh's native MSH format. The official Gmsh file-format documentation is available at [Gmsh file formats](https://gmsh.info/doc/texinfo/gmsh.html#MSH-file-format).

The native MSH format stores mesh data and associated model metadata. A minimal mesh contains `$MeshFormat`, `$Nodes`, and `$Elements` sections. Physical groups, model entities, periodicity information, and post-processing data can be stored in additional sections.

### Formats generated by SMRT

The current examples use two MSH revisions:

| Mesh mode | MSH revision | Main sections in the current examples |
| --- | --- | --- |
| `structured` | 2.2 | `$MeshFormat`, `$PhysicalNames`, `$Nodes`, `$Elements` |
| `automatic` | 4.1 | `$MeshFormat`, `$PhysicalNames`, `$Entities`, `$Nodes`, `$Elements` |

The Gmsh format revision is recorded in the `$MeshFormat` section. The two revisions are different serialization formats for the same basic mesh concepts; SMRT reads both through the Gmsh Python API.

### Physical groups

The current two-dimensional examples define:

- one two-dimensional physical group for each material region;
- one one-dimensional physical group named `_boundary` for the external boundary.

For example, the material physical groups in a three-material case are named according to the input-card materials, such as `uo2`, `zr`, and `h2o`.

There are two different numbering conventions to keep separate:

1. Gmsh node, element, entity, and physical-group tags are Gmsh tags. They are positive identifiers in the `.msh` file.
2. SMRT material IDs in the ALPHA `.trk` file are zero-based indices into the material-name list created by the input card.

Thus, a material may have a Gmsh physical-group tag of `1` while its SMRT/ALPHA material ID is `0`.

### Nodes

The `$Nodes` section stores node tags and coordinates. SMRT generates two-dimensional models, so the coordinates are written as `(x, y, z)` with `z = 0`. The pin-cell center is always placed at `(0, 0)`.

### Elements

The `$Elements` section stores element tags, element types, element tags/physical-group information, and node connectivity. In the current first-order two-dimensional examples:

- element type `1` represents a two-node boundary line;
- element type `2` represents a three-node triangle;
- element type `3` represents a four-node quadrilateral.

The physical group associated with a two-dimensional element identifies the material region used by the SMRT parser. Boundary line elements are associated with the `_boundary` group.

## ALPHA `.trk` files

The `.trk` files generated by the example input cards are written with:

```python
TrackFile(path, "alpha")
```

They are text files designed for the ALPHA neutron lattice physics code. ALPHA reads the file, stores the information in arrays, and uses the arrays in the MOC calculation.

The writer emits the following logical order:

```text
GeomType
PART_0_PIN_INFO
PART_1_PIN_LAYOUT_INFO
PART_2_RAY_PARAM_INFO
PART_3_RTM_GEOM_INFO
```

Lines beginning with `!` are comments or field headers. Blank lines and separator lines are part of the human-readable layout and should not be interpreted as data records.

### `GeomType`

The first line identifies the boundary geometry:

| Value | Meaning |
| --- | --- |
| `0` | square/rectangular geometry |
| `1` | complete hexagonal geometry |
| `2` | one-sixth symmetric hexagonal geometry |

### `PART_0_PIN_INFO`

This section assigns mesh regions to materials and FSR IDs. It begins with:

```text
NumOfPins <number_of_pins>
!pin_id  rtm_id  num_of_fsr  mat_id  fsr_id  //face_id
```

For each pin/RTM, the first line contains:

| Field | Meaning |
| --- | --- |
| `pin_id` | Physical pin ID written by the `RayTracingModule` |
| `rtm_id` | RTM ID |
| `num_of_fsr` | Number of flat-source regions associated with this pin/RTM |
| `mat_id` | Zero-based material ID |
| `fsr_id` | FSR ID used by the track data |
| `face_id` | Original mesh face ID, written after `//` as a reference/comment field |

The first FSR record of a pin is written on the same line as the pin/RTM header. The remaining FSR records contain the material ID, FSR ID, and mesh face reference with blank spacing in the pin-level columns.

The material ID is determined by the order of the `Material.Material` objects in the model input card, starting from zero and ending at `number_of_materials - 1`. The `fsr_id` is a region index and must not be confused with the material ID.

### `PART_1_PIN_LAYOUT_INFO`

This section stores the pin-map and sublayer information used by the ALPHA input layout:

```text
NumOfPinMaps <number_of_pin_maps>
NumOfSublayers <number_of_sublayers>
!id  dim_X  dim_Y  width_Z  mesh_Z
```

Each layout record contains:

| Field | Meaning |
| --- | --- |
| `id` | Pin-map ID |
| `dim_X` | Number of pins in the X direction |
| `dim_Y` | Number of pins in the Y direction |
| `width_Z` | Width of the Z-direction layout region |
| `mesh_Z` | Number of axial subdivisions/sublayers |

The layout matrix following each header row stores the RTM/pin IDs. The current single-pin examples contain one pin map and one axial sublayer.

### `PART_2_RAY_PARAM_INFO`

This section stores the characteristic-line parameters for every azimuthal direction:

```text
NumOfAzimAng <number_of_azimuthal_directions>
!azim  numU  numV  effAzim               effSpacing
```

Each azimuth record contains:

| Field | Meaning |
| --- | --- |
| `azim` | Global azimuth ID |
| `numU` | Number of tracks in the U family for the corresponding local direction |
| `numV` | Number of tracks in the V family for the corresponding local direction |
| `effAzim` | Effective azimuthal angle in radians |
| `effSpacing` | Effective characteristic-line spacing/width |

For the second half of the angular directions, the writer adds `pi` to the corresponding local azimuth angle. The effective spacing is written after track generation and can differ slightly from the requested nominal spacing because of the boundary geometry and track discretization.

### `PART_3_RTM_GEOM_INFO`

This section contains the region and characteristic-line data required by the MOC calculation. Its global header is:

```text
TotalNumOfRTM <number_of_rtms>
TotalNumOfFSR <total_number_of_fsrs>
TotalNumOfTrk <total_number_of_tracks>
TotalNumOfSeg <total_number_of_segments>
RTMWidthX <width_in_x>
RTMWidthY <width_in_y>
```

The totals are accumulated over the RTMs passed to the exporter. The geometry width is obtained from the mesh bounding box of the first RTM.

#### `RTM_ID`

For each unique `RTM_ID`, the writer emits one geometry block. If the input list contains repeated RTM IDs, the detailed geometry block is written only once for that ID.

#### `FSRAreaInfo`

The FSR-area subsection is:

```text
FSRAreaInfo
NumOfFSR <number_of_fsrs>
!fsr_id  fsr_area
```

Each record contains:

| Field | Meaning |
| --- | --- |
| `fsr_id` | FSR/mesh-region index |
| `fsr_area` | Area of the corresponding mesh region |

The area is obtained from `rtm.mesh.getArea(face_id)` and is written with 16 digits after the decimal point. This subsection does not repeat the material ID; the FSR-to-material mapping is provided in `PART_0_PIN_INFO`.

#### `TrackInfo`

The track subsection begins with a geometry-dependent header.

For square/rectangular geometry:

```text
!azim_id  num_ray  ray_id  num_seg  seg_id  seg_length          fsr_id
```

For hexagonal geometry:

```text
!azim_id  num_ray  ray_id  next_azim_id  next_ray_id  num_seg  seg_id  seg_length          fsr_id
```

The track-level fields are:

| Field | Meaning |
| --- | --- |
| `azim_id` | Global azimuth ID of the characteristic line |
| `num_ray` | Total number of characteristic lines for this azimuth |
| `ray_id` | Characteristic-line index within this azimuth |
| `next_azim_id` | Hexagonal reflection/continuation azimuth ID |
| `next_ray_id` | Hexagonal reflection/continuation line ID |
| `num_seg` | Number of segments on this characteristic line |

The `next_azim_id` and `next_ray_id` fields are written only for hexagonal geometry. They are obtained from the segmentation fields `mirror_azim_idx` and `mirror_track_idx`. The actual reflected angle is obtained by using `next_azim_id` as an index into the azimuth table in `PART_2_RAY_PARAM_INFO`.

For each track, the segment records contain:

| Field | Meaning |
| --- | --- |
| `seg_id` | Segment index along the characteristic line, starting from zero |
| `seg_length` | Length of the segment |
| `fsr_id` | FSR crossed by the segment |

The `fsr_id` in a segment record is obtained from the swept mesh face. It identifies the material region indirectly through the `PART_0_PIN_INFO` mapping. It is not a material ID.

The writer prints the `azim_id`, `num_ray`, and track-level identifiers on the first line of each characteristic line or azimuth block. Continuation lines contain the segment ID, segment length, and FSR ID with whitespace used to inherit the corresponding track-level fields. A dashed `!` separator is written after every track.

### Example interpretation

If a track record contains `num_seg = 3`, the following three segment records describe the complete path of that characteristic line through three consecutive mesh regions. ALPHA uses the segment lengths and FSR IDs to assemble the MOC sweep. The material associated with each segment is recovered through the FSR-to-material mapping in `PART_0_PIN_INFO`.

## Other `TrackFile` output mode

`TrackFile` also contains a `zmoc` formatter. That formatter writes an HDF5 file with groups such as `PinInfo`, `RayParamInfo`, and `Segmentation`. The public examples use the `alpha` formatter and therefore generate the text `.trk` format described above.

## Regenerating the files

The `.msh`, `.svg`, and `.trk` files can be regenerated from each example's `model.py` and `tracking.py` input cards. The input-card material order, geometry parameters, mesh parameters, tracking spacing, and azimuthal count determine the generated data.
